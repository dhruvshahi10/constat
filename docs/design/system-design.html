Constat System Design

Every security answer rests on an owned, expiring, exception-carrying claim, or it is refused and routed to the person who can fix it. This page shows how to use the product and how it is built.

How to use it

A reviewer's day, in seven steps

The order is the order you work in. Screens are from the web app in its standalone dark theme, except step 7, which runs inside Atlan in the light theme.

  1. Seed claims from what you already sent

    Open Claims, Import and drop in an answered questionnaire. Each answer becomes one of three things: a reusable answer on a claim that already covers it, a draft claim (questions that ask the same thing share one), or a skip with the reason named. Pick an owner per draft and commit. Every draft waits for a second person to approve it.

  2. Upload a questionnaire

    Open Inbox and upload an xlsx, csv or docx. The layout is found by header names, so the question column can sit anywhere. Each question moves through its states live. Anything that reads as instructions to a machine is quarantined before a model sees it.

  3. Work the review queue

    Open Review. The queue is ranked by deal value, deal blockers and age, so the oldest hard question rises. Each draft shows the claim it rests on, its owner, its version, and the change against the last answer you approved.

    j ka approvee editr routes send

    An edit is checked again like any draft. Approving writes the answer back to the claim, so the next identical question is reused. Sending records the customer, the approver and the exact claim version.

  4. Read the refusals

    A held or refused question shows the draft struck through and the gate that stopped it: no certificate behind a certification answer, an exception left out, a number the claim never stated, contract wording. Route it to the named owner with a deadline. Their answer becomes a claim once.

  5. Owners approve proposals

    Owners see proposals under Claims, Proposals: new claims from imports and routed questions, and changes from reviewer edits that rewrote more than 30 percent of an answer. The person who proposed a change cannot approve it. Freshness lists what expires, grouped by owner.

    Proposals and freshness are lists by owner. A failing Vanta test also lands here: the claim is proposed stale with a seven-day decision for its owner, and nothing is unpublished automatically.

  6. Watch what is still hard

    Metrics leads with the oldest open hard question, not an automation rate. Counts are per difficulty class: reused, covered, parameter missing, novel, contractual. Shipped-wrong is the stop signal. If the primary reviewer is silent for 72 hours, the banner says what keeps flowing and what is held, and deal blockers go to the named backup.

  7. Use it inside Atlan, and from agents

    Inside Atlan the same screens load in the sidebar under /embed, in the light theme, signed in as the Atlan user. Agents such as the Slack security agent call the MCP server: answer_question returns a verdict and never sends; write tools return a proposal.

Run it on your laptop

Four commands from the repo root. The seed script builds a demo tenant with two deals, two processed questionnaires and a reviewer who has been away four days.

# 1. install
python -m venv .venv && .venv/bin/pip install -r requirements.txt -r requirements-dev.txt
# 2. seed a demo tenant
CONSTAT_ENV=dev DATABASE_URL=sqlite:///data/sidecar.db CLAIM_STORE_PATH=data/claims .venv/bin/python scripts/seed_demo.py --tenant acme
# 3. start the API on :8000
CONSTAT_ENV=dev CONSTAT_DEV_TOKEN=dev CONSTAT_TENANT=acme DATABASE_URL=sqlite:///data/sidecar.db CLAIM_STORE_PATH=data/claims .venv/bin/uvicorn api.main:app --port 8000
# 4. start the web app on :3000, then open /review
cd web && npm ci && NEXT_PUBLIC_API_BASE=http://localhost:8000 NEXT_PUBLIC_DEV_TOKEN=dev npm run dev

System design

One questionnaire, end to end

Two things carry the design. The model writes text; deterministic code decides whether that text may leave. And nothing leaves without a person, who closes the loop by writing answers back into the claim store.

Deployment and trust boundaries

Where it runs and what crosses each line

Claims live in the customer's own Atlan glossary. Constat holds the work around them: questionnaires, review actions, metrics. Each arrow below is a boundary crossing with its own control.

The life of one question

Every question is always in exactly one state

A question that silently stops moving is the failure a managed questionnaire service suffers most. Here each change is an explicit transition; an illegal one raises, and every one writes a review action and a metric event.

The gates

Eleven checks, in this order, on every answer

Order matters: the first check that fires decides the outcome and the route. Every check reads canonical text, so zero-width characters, look-alike letters and "ninety days" written in words do not slip past.

#CheckWhat it catchesOutcome
0InjectionInstructions to a machine inside the questionREFUSE account team
1Legal commitmentLiability, indemnity, warranties, guaranteesHOLD Legal
2No covering claimA question nobody has answered beforeREFUSE domain owner, once
3Claim usableDraft, expired, deprecated, or a narrower audience than askedREFUSE or HOLD claim owner
4Certification evidenceA certification answered from a policy or a roadmapHOLD a person phrases it
5RelevanceA claim that answers a narrower question than the one askedHOLD
6Parameter missingThe question asks for a value; the claim states a principleHOLD owner adds the value
7CompletenessTrue but incomplete: an exception on the claim left outREFUSE
8AbsolutesAlways, never, 100 percent, unhackableREFUSE
9New valuesA number, version or period the claim never statesHOLD owner
10Contract wordingSLAs, notification windows, "commit to", in the question or the draftHOLD a person decides

Everything that passes is ANSWER, which still means "show a reviewer", never "send".

The sidecar database

  • questionnaires with the detected layout, so export survives a restart
  • question items with state, difficulty class, verdict and route
  • review actions with the answer before and after every edit
  • deals, which rank the queue and gate automation
  • metric events for every state change, edit, follow-up and model call
  • degradation state, the named backup and the automation level
  • model evaluation records, one per model and prompt version
  • principals, hashed tokens and Atlan users

SQLite on a laptop and in CI, Postgres when hosted. Both run the same tests.

Automation

What may ever go out without a person

LevelSends on its own
1 (pilot)Nothing. Every answer is reviewed.
2Reused answers, to customers marked approved, when the claim is fresh and unchanged since approval.
3Also covered answers, after four weeks with a human edit rate at or below 10 percent and nothing shipped wrong.

With the reviewer away 72 hours, nothing ships at a lower bar; the account executive gets a dated status and deal blockers go to the backup.

Never automated, at any level

  • A new contractual commitment
  • An answer to a question no person has answered before
  • Disclosing sensitive internals such as pen test findings
  • Publishing to the public trust centre
  • Correcting or declining a customer

Decisions that shape it

Six choices, and what each one rejected

ChoiceRejectedWhy
Gates in code decide releasePrompt-only guardrailsA prompt is not a control; swapping the model changes fluency, not safety.
Questions match claims, not documentsRetrieval over policy chunksA chunk cannot carry an owner, an expiry or the exceptions that must travel with it.
Writes are proposals; a second person approvesDirect edits to claimsMirrors Atlan's own MCP write tools; a reviewer's phrasing is not the owner changing a fact.
Versions are content hashesInteger versionsGlossary terms change in place; a hash proves what a sent answer rested on.
Two exports: customer and internalOne file for bothThe customer copy carries only sent answers and neutralises spreadsheet formulas.
Vanta failure opens a decisionAuto-unpublishOne failing host does not make "we encrypt at rest" false; a person decides within seven days.

The full log is DECISIONS.md in the repo; every entry names the alternative it rejected.
