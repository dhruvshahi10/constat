On the table

Three decisions that need a ruling today

Each blocks a sprint. Recommendation is marked; the alternative is stated fairly.

1. Where embeddings run

Blocks Sprint 3

Local model — recommended

Evidence text never leaves the process. Costs one heavy pinned dependency and breaks the current near-zero-install story, but keeps the trust posture we sell on.

Hosted embedding API

Lighter to install and better recall out of the box. Ships customer policy text to a third party — which we would then have to disclose in the very questionnaires we answer.

Why: we sell evidence custody. An architecture that egresses evidence to improve retrieval trades the product's premise for a metric.

2. What the review queue is built in

Blocks Sprint 2

Extend the stdlib console — recommended

One UI codebase, no install, reuses the run-report design system and the same pipeline the tests exercise. Costs us hand-written form handling.

Streamlit, per the directive

Faster to a working queue and a diff view. Adds a second UI stack, a second answer path to keep honest, and an install step for the reviewer.

Why: DECISIONS.md already chose stdlib for the client UI on these exact grounds. Overriding it is fine — but it needs a dated entry, not a drift.

3. How live drafters enter CI

Blocks Sprint 1

Recorded fixtures plus nightly live smoke — recommended

Deterministic, free, and blocks merges. The nightly run catches provider drift — the exact failure that already bit us when Google retired dated Gemini models.

Live keys on every CI run

Maximum realism. Flaky on rate limits, costs money per push, and leaves the suite dependent on a third party's uptime to merge a typo fix.

Why: the constitution has to be runnable offline by anyone who clones the repo.

Risk register

What could actually derail this

High

No design partner by Sprint 3Phase 2 gets built against an imagined reviewer, and we discover the queue is wrong after we have paid for it.

Mitigation → founder track starts Sprint 1, not Sprint 2. Partner conversations are on the critical path, not beside it.

High

Semantic retrieval quietly widens the tenant boundaryAn index is a second copy of the evidence. Isolation currently holds because the store is scoped; an index can leak across tenants at build time.

Mitigation → namespace enforced at build and query, with a cross-tenant eval that fails the build, written before the index.

Medium

Provider drift breaks the live path silentlyAlready happened once: Google retired dated Gemini models for new accounts while still listing them.

Mitigation → rolling alias is in place; nightly smoke turns the next occurrence into an alert instead of a demo failure.

Medium

Coverage pressure erodes a gateThe temptation at 83% will be to loosen the contradiction or staleness rule to reach 90%.

Mitigation → coverage is a target; zero unsupported claims is a blocker. Only a dated DECISIONS.md entry may touch a gate.

Definition of done

What "pilot-ready" means on 11 October

  1. Zero unsupported material claims — unchanged, under all three drafters, on a real customer's workbook.
  2. No delivered row without a named human — the simulated reviewer is gone from the product path, and an eval proves it cannot be bypassed.
  3. Cited coverage ≥ 83% — with every remaining refusal traceable to a correct gate, never a retrieval miss.
  4. ~20 evals green in CI — including recorded live-drafter fixtures and a cross-tenant index test.
  5. Two commands from clone to completed run — pinned dependencies, no manual setup.
  6. One design partner's real questionnaire — ingested in its native format, reviewed by their named GRC lead, delivered back with the audit chain intact.
